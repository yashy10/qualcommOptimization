# Minimalist Edge AI Challenge: baseline

## Final submission and repository contents

The selected model is **B3 (`b3_kd_lr001_e3_int8`)**, the MobileNetV2 with residual
blocks 6, 9 and 16 removed, three-epoch knowledge-distillation recovery at learning
rate 0.001, and static percentile INT8 quantization. Team: **Benson Edge**.
It achieves **98.84% accuracy**, **97.70% worst-class accuracy**, and **2.052 MiB**.
It is 17.6% smaller than the prior Q3a model for a 0.08-percentage-point accuracy
tradeoff. The recorded **1.110 ms** local median latency is provisional, measured
under background load; it is not a clean comparison with Q3a's milestone timing.

The dedicated Qualcomm RB3 Gen 2 profile reports **5.523 ms**, a **4.83x**
speedup over the recorded FP32 device profile. The new profile belongs to
this selected model, job `jp2oe0kxg`.

Final artifacts are in [`submission/`](submission/):

- [INT8 ONNX model](submission/student_model_int8.onnx)
- [Submission metrics and measurement provenance](submission/metrics.json)
- [Technical report with dashboard appendix (3 pages)](submission/technical_report.pdf)
- [Main technical report (2 pages)](submission/technical_report_2page.pdf)
- [Editable LaTeX report source](submission/report_source/technical_report.tex)

To reproduce the selected run in a **fresh workspace**, install `requirements.txt`,
provide the supplied student and ResNet-50 teacher checkpoints plus EuroSAT images,
and run `sh reproduce_selected.sh` with the environment's Python on PATH.
The original recovery used Apple MPS. Set `TRAIN_DEVICE=cpu` for CPU execution;
training time and floating-point results may differ. The script runs pruning,
adaptive BatchNorm, teacher caching, three recovery epochs, export verification,
and recalibrated static INT8 quantization. Saved subset indices are included.
Evaluate the rebuilt model with `measure.py`; run `timing.py` separately under
quiet mains-power conditions. The packaged `submission/code/` is a self-contained
source workspace once the supplied checkpoints and `data/` are placed inside it.

The repository includes source code, fixed image-index subsets, experiment configs,
model metadata, and recorded results. Downloaded EuroSAT images, the local Python
environment, supplied `.pt` checkpoints, cached teacher outputs, and intermediate
model binaries are excluded from Git. To reproduce experiments, place the supplied
student and teacher checkpoints in the project root and the EuroSAT dataset under
`data/`, then follow the commands below. The teacher is needed only for distillation
experiments. Intermediate models and teacher caches can be regenerated by the scripts.

Local baseline measurements are distinguished from organizer reference values.

A baseline is a set of measurements of the original, unchanged model. Every later
optimization is judged against it, so it has to be measured carefully and repeatably.

Our baseline is the supplied student model, `student_mobilenetv2_distilled.pt`
(a MobileNetV2 that sorts satellite images into 10 land-use classes).

## Evaluation data

Per judge instruction, accuracy is measured on the **full EuroSAT dataset, all 27,000
images, with no `val_split`**. Every result file records this as
`"split": "full_dataset_judge_instruction"`.

Because nothing is held out, the evaluation images include the ones used for
fine-tuning and calibration below.

## Official baseline

| File | Model | Runtime |
|---|---|---|
| `results/official_baseline_onnx_fp32.json` | `models/student_fp32.onnx` | ONNX Runtime |
| `results/official_baseline_pytorch.json` | `student_mobilenetv2_distilled.pt` | PyTorch |

The baseline scores 99.16% on all 27,000 images, and its weakest class is PermanentCrop
at 95.84%. Every other number is on the dashboard (next section).

All comparisons are against `official_baseline_onnx_fp32`, because the submission is an
ONNX file and ONNX Runtime is much faster than PyTorch for the very same model.

provided; the figures printed in the challenge PDF are kept apart in
`results/organizer_reference/`.

## Dashboard

Open `results/dashboard.html` in a browser. It is one file that works offline and shows:

- every saved result against the ONNX fp32 baseline, as a percentage and as a ratio
  (green is better, red is worse, grey is no change or smaller than run-to-run noise);
- accuracy for each of the 10 classes, with drops of more than 1 point highlighted;
- accuracy against file size and against latency, one point per experiment;
- the conditions of each run: background load, threads, energy mode, and whether the
  accuracy is official or a smoke test.

`measure.py` rebuilds the page after every run; `python dashboard.py` rebuilds it by
hand. Describe each experiment when you measure it, and the text appears in the
"What we did" column:

```bash
python measure.py models/student_int8.onnx --name static_int8 \
    --what "Static QDQ int8, 300 calibration images"
```

The dashboard reads the full results in `results/` only. Smoke tests and archived runs
are left out.

## Fixed image subsets

Both files are lists of image indices in torchvision's EuroSAT order, drawn class by
class with seed 42. `python make_subsets.py` recreates them byte for byte.

| File | Images | How it was drawn | Used for |
|---|---|---|---|
| `subsets/calibration_indices_300_seed42.json` | 300 | 30 from each class | Calibrating static quantization |
| `subsets/finetune_indices_20pct_seed42.json` | 5,400 | 20% of each class | Short recovery fine-tuning after pruning |

The 300 calibration images are all inside the fine-tuning subset, because both are the
first images of the same seeded shuffle.

To use one:

```python
import json
from torch.utils.data import Subset
from common import load_dataset

indices = json.load(open("subsets/calibration_indices_300_seed42.json"))["indices"]
calibration_set = Subset(load_dataset(), indices)
```

## Qualcomm AI Hub device

The target board is the Arduino UNO Q (Qualcomm Dragonwing QRB2210). No listed AI Hub
device uses that chip (`qai-hub list-devices`, checked 2026-10-13), so profiling uses
the closest low-power Qualcomm IoT device on the list:

**Dragonwing RB3 Gen 2 Vision Kit** (QCS6490, Qualcomm Linux 1.6).

Reasoning: among the five Qualcomm IoT devices listed, the QCS6490 is the lowest tier
(6-series; the others are 8- and 9-series chips) and the only one on a Linux build like
the UNO Q's. The Arduino VENTUNO Q is the same board family but carries a higher-tier
QCS8275, so its figures would be more optimistic. The RB3 Gen 2 is still well above a
QRB2210, so AI Hub latencies are a cross-check of relative gains, not UNO Q numbers.

Jobs are submitted with `python aihub_submit.py models/<model>.onnx --label <name>`
(target runtime ONNX; colliding `value_info` entries are stripped first) and recorded in
`results/ai_hub_jobs.json`. `python aihub_submit.py --status` prints their progress.

## Quantization

`python quantize.py --name <name> [--per-channel | --per-tensor] --calib-method
{minmax,entropy,percentile} --types {s8s8,u8s8} [--exclude-first-last]` runs
`quant_pre_process`, calibrates on `subsets/calibration_indices_300_seed42.json`,
quantizes in static QDQ format, writes `models/<name>.onnx` plus a `models/<name>.json`
sidecar of the exact settings, and runs `check_quant.py` (loads, static QDQ, size ratio,
agreement with fp32 on 500 images). Then measure it:

```bash
python measure.py models/<name>.onnx --name <name> --what "..."
```

## Pruning (PLAN_PRUNING.md)

Structured pruning with torch-pruning 1.6.1 (pinned in `requirements.txt`), seed 0.

| Tool | Purpose |
|---|---|
| `prune.py` | Depth pruning (residual blocks → `nn.Identity`), width pruning (torch-pruning, classifier ignored, `round_to=8`, global/uniform, magnitude/BN-scale/Taylor), adaptive BN; `--config configs/<name>.json` rebuilds any candidate exactly from the original checkpoint |
| `stage_a.py` | Stage A sweeps A1–A5: prune → adaptive BN → quick-eval → export check → `results/stageA/<name>.json` |
| `finetune.py` | Stage B recovery fine-tune (SGD lr 0.005, cosine, wd 4e-5, batch 32, 1–2 epochs, KD from cached teacher logits or `--no-kd`), plus the unseen-80% honesty check |

Pruning subsets (seed 0, stratified, fixed):

| File | Images | Use |
|---|---|---|
| `subsets/finetune_subset_20.json` | 5,400 (20%) | adaptive BN, fine-tuning, teacher-logit cache, Taylor gradients |
| `subsets/quickeval_subset_10.json` | 2,700 (10%), disjoint from the above | provisional Stage A scoring |
| `subsets/unseen_80_derived.json` | 21,600 | honesty check after fine-tuning (derived) |

Stage A accuracy is provisional (quick-eval subset); official accuracy is always
`measure.py` on all 27,000 images. Params and MACs for pruned models are thop counts on
the PyTorch model, comparable to the 2.237 M / 0.326 G PyTorch baseline. The dashboard has
a separate Stage A section with accuracy-vs-params, accuracy-vs-MACs and block-scan charts.

The earlier hand-written pruner (uniform hidden-channel pruning without a dependency
graph) is kept in `archive/prune_manual.py`; its no-fine-tune sweep models are in
`models/archive/prune_sweep_no_finetune/`.

## How to rerun the baseline

Close other apps, plug the laptop in, and run one command at a time.

```bash
source edge-ai-env/bin/activate

# 1. Check the ONNX export still matches the original model (about 20 seconds)
python verify_export.py

# 2. Quick smoke test on 200 images, saved to results/smoke/
python measure.py models/student_fp32.onnx --name smoke --limit 200 --runs 20 --energy-seconds 3

# 3. Official baseline on all 27,000 images (about 3 minutes for ONNX, 17 for PyTorch)
python measure.py models/student_fp32.onnx --name official_baseline_onnx_fp32 --overwrite
python measure.py student_mobilenetv2_distilled.pt --name official_baseline_pytorch --overwrite

# 4. Show everything side by side
python compare.py
```

`--overwrite` is only needed because those two results already exist. Without it,
`measure.py` refuses to replace a saved result.

If `verify_export.py` ever fails, rebuild the export with `python export_onnx.py` and
run it again. The supplied `.pt` files are only ever read, never written.

## What each measurement means

| Measurement | Plain meaning | How it is measured |
|---|---|---|
| Accuracy | How often the model names the right class | One pass over all 27,000 images |
| Per-class and worst-class accuracy | Accuracy for each of the 10 classes, and the weakest one | Same pass, counted per class |
| Parameters | How many numbers the model has learned | `thop` for PyTorch, counted from the graph for ONNX |
| File size | Space the model takes on disk | Size of the file in MB |
| MACs | Amount of arithmetic for one image (multiply-accumulate operations) | `thop` for PyTorch, counted from the graph for ONNX |
| Latency | Time to answer for one image | 100 timed runs after 10 warm-up runs; the dashboard shows the median, `compare.py` the average |
| Peak RAM | Most memory the program used while answering | Process memory sampled every 10 ms with `psutil` |
| Energy per prediction | Electricity used for one answer, in joules | `codecarbon` over 15 seconds of back-to-back predictions |

Each result file also records the machine, the runtime and its version, the thread
setting, the background CPU load, the power source and the exact method used.

Things to keep in mind when reading the numbers:

- **Energy is an estimate, not a sensor reading.** On this Mac, `codecarbon` works out
  power from how busy the CPU is. Each result says so in `energy_source`.
- **Compare ONNX with ONNX.** See the note under "Official baseline".
- **MACs differ slightly between the two formats.** Export merges some layers
  (BatchNorm into convolutions), so the ONNX count is a little lower than the `thop` count.
- **Latency and energy depend on what else the laptop is doing.** Measure the baseline
  and every later model on the same machine under the same conditions.
